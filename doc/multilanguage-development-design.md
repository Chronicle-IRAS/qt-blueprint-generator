# 多语言混合开发后续规划

> 文档定位：本文是 MVP 完成后的演进规划，不属于当前 MVP 的实施范围。当前 Task 1 至 Task 10 的实现文件、技术路线和验收标准均以 `doc/mvp-implementation-plan.md` 为准，不因本文而调整。

## 1. 决策

MVP 完成后的演进实现不限制为单一语言。Qt 是课题要求和桌面产品的核心技术，但后续不要求蓝图解析、AI 调用、提示词编译、代码生成等全部能力均使用 C++ 实现。

本文不改变正在进行的最小版本功能范围，也不参与当前 Task 的技术选型。只有原 MVP 完成并验收后，才按本文评估多语言接入；不得为了“多语言”重写已经完成或正在开发的 MVP 模块。

## 2. 不变的最小版本目标

最小版本仍然完成以下闭环：

1. 用户在 Qt 桌面程序中创建节点、填写说明并连接蓝图。
2. 系统检查蓝图结构，生成稳定的中间表示（IR）。
3. 系统依据 IR 和模块上下文构造提示词。
4. AI 按模块返回代码候选。
5. 用户查看、修改、接受或拒绝候选文件。
6. 系统构建验证并导出完整项目。

最小版本的生成目标仍限定为：

```text
Qt 6 Widgets + C++17 + CMake
```

“允许多语言实现”不等于首版同时生成 Python、Java、React 等多种项目。生成目标多样化仍属于后续扩展。

## 3. 设计原则

### 3.1 Qt 必须承担核心职责

Qt/C++ 至少负责：

- 桌面应用生命周期和主窗口。
- 蓝图画布、节点、端口、连线和交互。
- 属性面板、代码候选差异和构建日志展示。
- 本地项目的打开、保存、导入和导出操作。
- 后台服务的启动、停止、崩溃检测和状态展示。

这保证 Qt 不是简单套壳，而是产品的主要交互与本地工程宿主。

### 3.2 按问题选择语言

MVP 完成后推荐但不强制的职责划分：

| 组件 | 首选技术 | 原因 |
|---|---|---|
| 蓝图编辑器 | Qt 6/C++ | QGraphicsView适合节点画布和桌面交互 |
| 本地项目管理 | Qt 6/C++ | 便于处理文件选择、进程和界面状态 |
| 蓝图规范化与IR | Python | 数据转换、测试和迭代速度较快 |
| 提示词编译 | Python | 便于使用模板、JSON Schema及文本工具 |
| AI接口适配 | Python | 模型SDK和流式响应生态更丰富 |
| 代码候选校验 | Python | 便于解析响应、校验路径和组织文件 |
| CMake构建控制 | Qt 6/C++ | 使用QProcess并实时展示输出 |
| 生成项目代码 | Qt/C++ | 这是MVP唯一输出技术栈，不受实现语言影响 |

如果某个组件已经使用 C++ 稳定实现，不应仅为符合本表而迁移到 Python。

## 4. 推荐架构

```text
┌─────────────────────────────────────────────┐
│              Qt/C++ 桌面进程                │
│                                             │
│  蓝图画布  项目管理  差异确认  构建与导出   │
└───────────────────┬─────────────────────────┘
                    │ JSON-RPC 2.0 / stdio
                    │ 一行一个完整JSON消息
┌───────────────────▼─────────────────────────┐
│              Python 本地工作进程            │
│                                             │
│  蓝图校验  IR编译  提示词编译  AI调用       │
│  响应校验  候选代码组织  生成记录           │
└─────────────────────────────────────────────┘
```

桌面进程使用 `QProcess` 启动 Python 工作进程，并通过标准输入、标准输出交换结构化消息。最小版本不开放网络端口，也不引入独立服务器。

选择标准输入输出通信的原因：

- 适合单用户、本地桌面软件。
- 不需要端口发现、防火墙配置和服务注册。
- Qt 可以直接监控退出码、标准错误和崩溃。
- Python 工作进程可独立执行单元测试。
- 后续仍可在不改变上层业务接口的情况下替换为本地套接字。

## 5. 进程通信契约

通信采用 JSON-RPC 2.0 形式。每条消息序列化为单行 UTF-8 JSON，以换行符分隔。消息内部的文本换行必须由 JSON 转义。

### 5.1 健康检查

请求：

```json
{"jsonrpc":"2.0","id":1,"method":"health.check","params":{}}
```

响应：

```json
{"jsonrpc":"2.0","id":1,"result":{"status":"ok","protocolVersion":1}}
```

### 5.2 蓝图校验

请求：

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "blueprint.validate",
  "params": {
    "blueprint": {
      "schemaVersion": 1,
      "projectId": "login-demo",
      "nodes": [],
      "edges": []
    }
  }
}
```

响应：

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "valid": false,
    "diagnostics": [
      {
        "code": "missing_start",
        "severity": "error",
        "nodeId": "",
        "edgeId": "",
        "message": "蓝图必须包含一个开始节点"
      }
    ]
  }
}
```

### 5.3 最小方法集合

| 方法 | 作用 |
|---|---|
| `health.check` | 检查工作进程和协议版本 |
| `blueprint.validate` | 执行结构校验并返回诊断 |
| `ir.compile` | 将蓝图编译为稳定IR |
| `prompt.compile` | 为指定节点生成提示词 |
| `generation.generateModule` | 调用AI生成单个模块候选 |
| `generation.cancel` | 尝试取消尚未完成的生成请求 |

所有请求必须包含唯一 `id`。Qt 进程维护待处理请求表，工作进程必须原样返回请求 `id`，从而允许异步完成和乱序响应。

## 6. 跨语言数据边界

两个进程之间只传递 JSON 兼容的数据：

- 字符串、布尔值和有限范围数值。
- 数组和键值对象。
- 项目内部的规范化相对路径。
- 节点ID、文件哈希、生成批次ID。

禁止跨边界传递：

- C++对象地址或Python对象序列化结果。
- 任意可执行脚本。
- 未规范化的绝对输出路径。
- API密钥和完整环境变量列表。
- 二进制文件正文；二进制内容通过受控文件路径引用。

共享数据契约放在：

```text
schemas/
├─ blueprint.schema.json
├─ ir.schema.json
├─ generation-request.schema.json
└─ generation-result.schema.json
```

Schema 文件是进程边界的权威定义。Qt 和 Python 的类型都从同一 Schema 的字段约定实现，不允许分别维护两套含义不同的模型。

## 7. MVP 完成后的接入方式

多语言支持只在 MVP 验收完成后按以下顺序加入，不打断或替代当前 Qt 功能开发：

### 阶段A：冻结边界

- 保留现有蓝图编辑和项目文件格式。
- 确认 `blueprint.json` 的 schemaVersion 为1。
- 为后台能力定义抽象接口，不移动当前实现。
- 使用进程内假实现完成界面与测试。

### 阶段B：增加Python工作进程

- 新增独立 `worker/` 目录。
- 首先只实现 `health.check`。
- Qt 使用 QProcess 启动工作进程并完成握手。
- 工作进程不可用时，界面给出明确错误，不影响项目打开和蓝图编辑。

### 阶段C：逐项迁移后台能力

- 先接入 `blueprint.validate` 和 `ir.compile`。
- 验证跨语言结果与现有实现的测试样例一致。
- 再接入提示词编译和AI请求。
- 每次只替换一个接口，不同时重写多个模块。

### 阶段D：移除重复实现

- 只有Python实现通过全部契约测试后，才考虑删除对应的临时实现。
- 若现有C++实现更稳定，可以长期保留，不要求统一语言。

## 9. 测试要求

### 9.1 Qt/C++测试

- 蓝图画布和领域模型测试继续使用 Qt Test。
- 后台进程启动测试使用一个固定的测试工作进程。
- 覆盖工作进程不存在、握手失败、响应超时、崩溃和非法JSON。
- UI测试不访问真实AI服务。

### 9.2 Python测试

- 使用 pytest 测试校验、IR、提示词和响应解析。
- AI接口通过Fake客户端替代。
- 所有路径安全测试使用临时目录。
- 测试中不读取开发者真实API密钥。

### 9.3 契约测试

同一组 JSON fixture 同时用于 Qt 和 Python：

- 合法蓝图。
- 缺少开始节点的蓝图。
- 包含不可达节点的蓝图。
- 包含非法路径的生成结果。
- 正常和异常JSON-RPC响应。

契约测试必须验证：

- 双方字段名称和类型一致。
- 协议版本不兼容时明确拒绝连接。
- 中文、自定义文字和转义换行不会损坏消息边界。
- 同一蓝图产生语义等价的规范化IR。

## 10. 打包和运行

开发环境允许直接调用系统 Python。发布版本再考虑将 Python 运行时和工作进程一起打包。

后续混合开发版本的启动顺序：

1. Qt 桌面进程启动。
2. 定位配置的 Python 可执行文件。
3. 使用 QProcess 启动 `python -m blueprint_worker`。
4. 发送 `health.check`。
5. 协议版本一致后启用AI生成相关按钮。
6. 工作进程不可用时保持蓝图编辑、保存和导出已有结果的能力。

首版不要求解决所有平台的独立安装包问题。论文演示环境只需固定一套已记录版本的 Windows、Qt 和 Python 环境。

## 11. 安全边界

- Python 工作进程不得把日志写入标准输出；标准输出只用于协议消息，日志写入标准错误。
- AI返回的文件只能进入候选目录，不能直接覆盖当前项目。
- Qt 进程在接受候选前再次检查路径是否位于项目目录内。
- 构建必须由用户显式触发，AI响应完成后不得自动运行生成程序。
- API密钥只从运行环境或系统安全存储读取，不通过JSON-RPC发送。
- 外部代码默认不发送给AI；只有用户明确选择的接口摘要进入提示词。

## 12. 与原最小实现计划的关系

本文不调整原 MVP 实施计划。当前 Task 1 至 Task 10 继续按计划中的 C++ 文件、Qt 接口、测试和验收项实现；多语言工作进程不作为 MVP 完成条件，也不得用于跳过当前任务。

原计划中下列概念保持不变：

- 蓝图是唯一架构主数据源。
- 生成文件先进入候选目录。
- 人工修改不得被静默覆盖。
- 外部代码以黑盒模块导入。
- 基础工程和公共接口采用确定性生成。
- 真实AI调用不参与自动化测试。

原计划中的 `IAiClient`、IR 编译、提示词编译和响应解析仍在 MVP 阶段按原定 C++/Qt 方案实现。MVP 验收完成后，才允许在保持接口与契约兼容的前提下，将这些后台能力逐项替换为 Python 工作进程；Qt 侧届时维护稳定的后台服务接口和 JSON-RPC 客户端。

## 13. 后续混合开发版本的验收增量

以下要求只适用于 MVP 完成后的混合开发版本，不计入当前 MVP 验收：

- Qt 能启动和关闭 Python 工作进程。
- 启动后能完成带版本号的健康检查。
- 工作进程崩溃不会导致未保存蓝图丢失。
- 非法或未知JSON-RPC响应会被拒绝并记录诊断。
- Qt和Python契约测试使用同一组fixture并全部通过。
- 没有Python环境时，用户仍可编辑和保存蓝图。
- 多语言接入没有改变现有 `blueprint.json` 的语义。

## 14. 结论

MVP 完成后，允许多语言混合开发能够提升 AI 接入和代码生成部分的迭代效率，同时保留 Qt 在桌面图形编辑、项目管理和本地工程操作方面的优势。合理的演进方案不是把项目拆成大量微服务，而是保持两个本地进程和一个稳定 JSON 契约：Qt 负责产品主体，Python 负责适合快速迭代的后台能力。

当前实现不进行迁移。先完整完成并验收 MVP，再沿稳定接口逐步接入 Python 工作进程，是风险最低的实施方式。
